O que falta para atingir 100% sem overfitting?

Para chegar a 100% em novos sistemas sem overfitting, o principal desafio não parece ser criar regras mais específicas, mas reduzir a incerteza na inferência das interações. Os serviços já são recuperados com altíssima qualidade; o erro residual está principalmente em decidir quando uma relação entre dois serviços é realmente necessária. Isso exige uma forma generalizável de validar dependências, não uma lista de relações esperadas. Além disso, 100% provavelmente não deve ser o objetivo metodológico: o objetivo mais defensável é obter desempenho muito alto e estável em sistemas não vistos.

Precisa de requisitos melhores?

Sim, até certo ponto. Requisitos mais claros, completos e consistentes reduzem a ambiguidade e naturalmente melhoram a geração, mas não resolvem tudo. O próprio artigo mostra que mesmo com requisitos cuidadosamente curados o problema das interações permanece. Portanto, requisitos melhores são uma condição importante para atingir o potencial do pipeline, mas o ganho adicional precisa vir do raciocínio/validação arquitetural dos agentes.

Qual é o mínimo de conhecimento do sistema que o pipeline exige hoje?

Hoje, o mínimo real é um conjunto de requisitos textuais e, para a avaliação, um mapa de normalização dos nomes. O pipeline não precisa conhecer previamente os serviços esperados, as interações corretas ou a arquitetura do sistema para gerar a solução. Isso já é uma vantagem importante, porque mantém o método requirement-driven.

Qual seria o mínimo ideal para justificar o empenho?

O cenário ideal seria exigir somente requisitos funcionais textuais bem estruturados, sem código-fonte, sem arquitetura de referência e sem regras específicas do domínio. Opcionalmente, poderia existir apenas um pequeno contexto textual do domínio quando os requisitos forem ambíguos. Se conseguirmos manter desempenho próximo ao atual nesse cenário em vários sistemas inéditos, aí a proposta ganha uma justificativa forte: um pipeline reutilizável que transforma requisitos em uma arquitetura inicial de microsserviços com pouca intervenção humana.

Por que alguém usaria nosso pipeline em vez de simplesmente chamar uma LLM?

Esse é provavelmente o maior argumento de valor do trabalho. Uma chamada direta a uma LLM gera uma resposta; o seu pipeline transforma a tarefa em um processo com papéis especializados, validação e consolidação. Na prática, isso pode oferecer maior controle, rastreabilidade, possibilidade de detectar e corrigir erros, comportamento mais reproduzível e uma arquitetura final baseada em múltiplas análises em vez de depender do julgamento de uma única geração. Portanto, a proposta não precisa ser “LLM melhor que LLM”; ela pode ser “processo arquitetural mais confiável e reutilizável do que uma geração direta”.

Sobre substituir uma RAG

A ideia faz sentido como protótipo de “memória arquitetural” antes da implementação da RAG. A biblioteca de exemplos no prompt funciona como um conjunto fixo de conhecimento geral sobre padrões de dependência. Posteriormente, a RAG poderia substituir essa biblioteca estática por recuperação dinâmica de exemplos relevantes, sem mudar necessariamente o raciocínio do agente.

A diferença para overfitting é importante:

Prompt anterior: poderia ser considerado mais vulnerável a overfitting porque, à medida que observávamos PetClinic e Bookstore, fomos introduzindo conhecimento e regras cada vez mais alinhados ao comportamento desses benchmarks. Isso aumenta o desempenho nos casos conhecidos, mas pode não transferir para sistemas novos.

Novo prompt: os exemplos são deliberadamente independentes dos benchmarks e ensinam relações abstratas como “serviço A precisa de dados pertencentes a B”, “não inferir relações transitivas”, “não criar uma malha completa”, “não confundir vocabulário compartilhado com dependência”, etc. O agente recebe regras de raciocínio, não respostas para os sistemas avaliados. Portanto, não considero essa biblioteca de exemplos overfitting, desde que você mantenha uma regra rígida: não acrescentar posteriormente exemplos derivados dos erros específicos de PetClinic ou Bookstore.

E existe uma vantagem experimental interessante: você pode mais tarde substituir INTERACTION_EXAMPLES por uma RAG de exemplos externos, sem alterar o objetivo do agente. Isso permite comparar claramente:

Prompt básico → Prompt com biblioteca geral → Prompt + RAG

e medir se o conhecimento arquitetural recuperado realmente melhora a generalização.

Ter um few-shot com uma boa biblioteca de exemplos é fundamental, com o cuidado de nao entregar detalhes daqueles sistema em si, mas possuir situações semelhantes para ser aplicado em diversas situações. Precisamos identificar quais eram os atalhos específicos que faziam A acertar os benchmarks e substituí-los por princípios gerais equivalentes. Do pipeline inicial para a versão atual, **não temos mais**:

* **Regra literal baseada no benchmark:** instruções específicas sobre PetClinic/Bookstore ou seus serviços esperados.
* **Conhecimento da arquitetura correta dos sistemas avaliados** inserido direta ou indiretamente nos prompts.
* **Liberdade arquitetural ampla** para o agente criar serviços apenas porque uma decomposição DDD seria plausível.
* **Few-shot contendo uma decomposição do próprio sistema-alvo**; agora o exemplo é tratado apenas como referência de formato.
* **Orientação genérica fraca sobre precisão**; agora há uma política explícita para excluir serviços e interações sem evidência suficiente.
* **Menos restrições contra over-segmentation:** agora CRUD, entidades, atributos, telas, atores e convenções técnicas não justificam, sozinhos, novos serviços.
* **Menos controle sobre infraestrutura:** agora gateway, discovery, config, admin, monitoring etc. só entram quando exigidos pelos requisitos.
